# MVP 설계와 테스트 전략

목적은 기능 수보다 사용자 흐름, 상태 전이, 권한, 데이터 무결성을 검증하는 방법을 보여주는 것입니다.

## 계층

React → Express REST API → SQLite. 화면은 사용자 피드백을 맡고, API는 인증·시간 범위·소유권을 검증합니다. DB는 동일 슬롯에 여러 확정 예약이 생기는 것을 최종 방어합니다. 단일 Node 프로세스의 동기 DB 작업은 순차 처리됩니다. 동시 요청 테스트는 경쟁 요청 중 한 건만 성공하는지 검증하며, 다중 서버 부하 테스트를 대신하지 않습니다.

예약은 물리 삭제하지 않고 취소 이력을 보존합니다. 세션은 임의 토큰을 HttpOnly/SameSite 쿠키로 저장하고 서버 메모리에서 사용자에 연결합니다. 외부 Origin의 상태 변경 요청은 거부합니다. 실제 배포용 인증은 범위 밖입니다.

## API 계약

### 예약 저장과 ID (2026-09-28 변경)

`bookings`는 `id`, `user`, `slot`, `status`를 저장한다. 1시간 슬롯마다 한 행이며, 화면에서 연속 시간이 묶여도 DB 행은 각각 유지한다. 취소는 행 삭제 대신 `status`를 `confirmed`에서 `cancelled`로 변경한다.

신규 예약 ID는 `20260928-0001` 형식이다. 앞 8자리는 이용 날짜가 아니라 예약 생성 시점의 KST 날짜이고, 뒤는 해당 날짜 전체 사용자 공통의 슬롯별 순번이다. 하루 첫 번호는 0001이며 최소 4자리로 표시한다(9999 다음은 10000). 복수 예약은 요청 배열 순서로 번호를 받으며 한 요청 안에서는 같은 생성 날짜를 사용한다.

`booking_sequences(date, value)`에 날짜별 마지막 순번을 저장한다. `BEGIN IMMEDIATE` 예약 트랜잭션 안에서 순번 증가와 예약 삽입을 함께 처리하므로 경쟁 요청이 같은 번호를 발급하지 않는다. 예약 실패 시 순번 증가도 롤백한다. 취소 시 순번을 되돌리지 않으며 서버 재시작 후에도 이어진다. 기존 UUID 예약은 변경하지 않고 조회·취소할 수 있다. 로그인 세션 토큰은 계속 무작위 UUID를 사용한다.

예: 2026-09-28에 내일 09·10시 예약 시 ID는 `20260928-0001`, `20260928-0002`이며 slot은 각각 `2026-09-29T09:00:00+09:00`, `2026-09-29T10:00:00+09:00`이다. 예약 ID는 사용자에게 접근 권한을 부여하는 비밀값이 아니며 조회·취소는 서버의 소유권 검증을 거친다.

| 메서드·경로 | 용도 | 대표 응답 |
|---|---|---|
| POST /api/login | username, password로 데모 로그인 | 200 / 401 |
| POST /api/logout | 세션 제거 | 200 |
| GET /api/me | 현재 사용자 | 200 / 401 |
| GET /api/slots?date=YYYY-MM-DD | 시간별 가용 여부 | 200 / 400 / 401 |
| GET /api/bookings | 내 예약 이력 | 200 / 401 |
| POST /api/bookings | `{slot: ISO 시각 +09:00}` 또는 같은 날짜 `{slots: [...]}`(1~9개) | 201 / 400 / 401 / 409 |
| POST /api/bookings/:id/cancel | 본인 예약 취소 | 200 / 401 / 404 |
| POST /api/bookings/cancel | `{ids: [...]}`(1~9개) 본인 예약 묶음 취소 | 200 / 400 / 401 / 404 |
| PUT /api/admin/slots | `{slot, blocked: boolean}` | 200 / 400 / 401 / 403 / 409 |

## 레이어 선택

| 검증 | 레이어 | 이유 |
|---|---|---|
| 미인증, 비밀번호 오류, 타인 취소, 관리자 권한 | API | 화면을 거치지 않고 서버 규칙 확인 |
| 과거·30일 초과·영업시간·정각·날짜 형식 | API | 입력 조합을 빠르고 명확하게 검증 |
| 동시 예약 요청 중 하나만 성공 | API | 독립 사용자 세션으로 경쟁 요청 구성 |
| 중복 제약, 취소 이력, 재예약 데이터 | DB + API | 저장소 불변 조건과 공개 동작 각각 확인 |
| 로그인 → 예약 → 새로고침 → 취소 | E2E | 사용자 흐름과 화면·API 연결을 검증 |
| 예약 API 503 피드백 | E2E mock | 장애를 재현하고 버튼 재활성화 확인 |
| 현재 시각·30일 경계, 과거 예약 취소 | API + 시계 고정 서버 | 서버 시간을 고정해 경계 시점을 정확히 재현 |
| 로그인 시간 초과·늦은 응답 | E2E + 브라우저 시계·fetch 대체 | 실제 대기 없이 10초 경계와 응답 순서를 제어 |

## 재현성과 한계

임시 DB를 실행 단위로 생성하고 실제 사용 DB와 분리합니다. API 테스트는 고유 날짜를 사용하고 생성 예약을 finally에서 취소합니다. 브라우저 컨텍스트는 테스트마다 격리합니다. worker 1개와 프로젝트별 테스트 파일로 공유 DB 경쟁을 제한합니다. 이 방식은 작은 MVP에 적합하며 병렬 확장 시 worker별 서버·DB 격리가 필요합니다.

서버 시간 경계(현재 시각, 정확히 30일 후, 과거 예약 취소)는 `Date.now()`를 고정한 테스트 전용 서버([clock-server.js](../tests/helpers/clock-server.js))에서 검증합니다. 운영 코드에는 시계 주입을 추가하지 않고 테스트 프로세스에서만 대체합니다. 브라우저의 10초 제한은 Playwright 시계로 제어합니다. DB 테스트는 인메모리·임시 DB에서 스키마 불변 조건, 재연결 후 유지, ID 순번을 확인하며, API가 사용하는 실제 DB 파일을 직접 조회하는 통합 검증은 후속 과제입니다.
