# 로그인 테스트 케이스
## 1. 기준 문서
- [요구사항](requirements-final.md)

## 2. 작성 기준
- 케이스 ID는 `TC-L-01`부터 순서대로 부여합니다.
- 각 케이스에 검증하는 요구사항 ID를 연결합니다.
- 절차와 기대 결과는 다른 사람이 그대로 수행하고 판정할 수 있게 작성합니다.
- 우선순위는 P1(실패 시 보안·데이터 무결성이 깨지거나 대부분의 사용자가 핵심 흐름을 이용할 수 없음), P2(드물게 발생하거나 재시도로 복구 가능한 장애 안내·표시·경계 조건)로 구분하고 선택 이유를 적습니다.
- 테스트 레이어는 API, E2E, 통합 중 선택하고 이유를 적습니다.
- 자동화 상태는 미구현 / 부분 구현 / 구현으로 기록합니다. 코드가 있다는 사실은 실행 통과를 의미하지 않습니다.
- 색상·테두리 등 시각적 외형은 디자인 변경에 민감하므로 자동화 범위 밖으로 정의합니다. 자동화 상태는 외형을 제외한 기대 결과를 기준으로 판정하며, 외형 항목은 필요 시 수동으로 확인합니다.
- 실제 실행 일시·환경·통과·실패·증거는 별도 [테스트 리포트](login-test-report.md)에 기록합니다.

## 4. 상세 케이스
### `TC-L-01` 로그인 입력란 초기값

- **요구사항 ID:** R-01
- **검증 목적:** 사용자가 입력하기 전 두 필드가 빈 값인지 확인한다.
- **우선순위 / 이유:** P2 / 로그인 폼의 초기 표시 조건을 확인한다.
- **테스트 레이어 / 선택 이유:** E2E / 화면 조작과 사용자에게 표시되는 결과를 검증한다.
- **자동화 상태:** 구현
- **연결 코드:** [login.e2e.spec.js](../tests/login.e2e.spec.js)의 `[TC-L-01]` 테스트

#### 사전조건

- 서버 실행 후 로그인 세션과 저장된 자동완성 정보가 없는 새 브라우저 컨텍스트에서 로그인 화면을 연다.
- 입력 조합별로 컨텍스트를 새로 준비한다.

#### 입력값 및 장애 조건

| 조합 | 입력 조건 |
|---|---|
| A | 입력·제출하지 않음 |

#### 수행 절차

1. 로그인 화면을 연 뒤 입력값을 변경하지 않는다.
2. 계정과 비밀번호 입력란의 실제 value를 확인한다.

#### 기대 결과

- 계정과 비밀번호의 value가 모두 빈 문자열 `""`이다. placeholder를 입력값으로 판정하지 않는다.

#### 종료 후 정리

- 브라우저 컨텍스트를 닫는다.

#### 비고

- 브라우저 비밀번호 관리자의 자동완성 동작은 이 케이스 범위 밖이다.

### `TC-L-02` 계정 미입력 로그인 시도

- **요구사항 ID:** R-01
- **검증 목적:** 계정 미입력 시 오류 안내, 요청 차단, 입력 후 오류 해제를 검증한다.
- **우선순위 / 이유:** P2 / 정상 로그인 경로를 차단하지 않고 사용자가 입력을 보완하여 복구할 수 있는 화면 검증으로, 핵심 인증 성공·실패 검증보다 낮은 우선순위로 분류한다.
- **테스트 레이어 / 선택 이유:** E2E / 입력란 강조, 오류 문구, 포커스와 브라우저의 로그인 요청 미전송을 함께 확인한다.
- **자동화 상태:** 구현 (시각적 강조는 자동화 범위 밖 · 수동 확인 항목)
- **연결 코드:** [login.e2e.spec.js](../tests/login.e2e.spec.js)의 `[TC-L-02]` 테스트 (A·B 독립 실행)

#### 사전조건

- 서버가 실행 중이며, 로그인 세션이 없는 브라우저에서 로그인 화면을 연다.
- 각 입력 조합은 새 브라우저 컨텍스트에서 독립적으로 시작한다.
- 제출 전부터 `POST /api/login` 요청을 기록한다. 초기 세션 확인 요청 등은 집계하지 않는다.

#### 입력값 및 장애 조건

| 조합  | 계정         | 비밀번호       |
| --- | ---------- | ---------- |
| A   | 빈 문자열 `""` | 빈 문자열 `""` |
| B   | 빈 문자열 `""` | `demo1234` |

#### 수행 절차

1. 해당 조합의 입력값을 설정하고 [로그인] 버튼을 선택한다.
2. 오류 문구, 입력란 강조, 포커스 위치와 로그인 요청 수를 확인한다.
3. 계정에 `alice`를 입력하고 계정 오류가 해제되는지 확인한다. 다시 제출하지 않는다.
4. 조합 A에서는 비밀번호 오류가 유지되는지 확인한 뒤 `demo1234`를 입력하고 비밀번호 오류가 해제되는지 확인한다.
5. 로그인 요청이 여전히 전송되지 않았는지 확인한다. 각 조합에서 위 절차를 독립적으로 수행한다.

#### 기대 결과

- 브라우저 기본 필수 입력 안내 대신 화면 내 오류가 표시된다.
- 두 조합 모두 계정 입력란이 강조되고 `계정을 입력해주세요.`가 표시되며 계정 입력란에 포커스가 위치한다.
- 조합 A에서는 비밀번호 입력란도 강조되고 `비밀번호를 입력해주세요.`가 함께 표시된다.
- 조합 B에서는 비밀번호 필수 입력 오류가 표시되지 않는다.
- 계정 입력 후 계정 오류 문구와 강조가 해제된다. 조합 A의 비밀번호 오류는 비밀번호를 입력할 때 해제된다.
- 전체 절차에서 `POST /api/login` 요청 수는 0건이며 로그인 화면을 유지한다.

#### 종료 후 정리

- 요청 기록을 종료하고 브라우저 컨텍스트를 닫는다.

#### 비고

- A·B 조합을 독립 테스트로 구현했다. 오류 문구·aria-invalid·포커스·요청 미전송·입력 후 오류 해제를 검증한다. 색상·테두리 두께는 디자인 변경에 민감하므로 자동 검증하지 않는다. 실제 시각적 강조와 해제는 수동 확인 대상으로 유지하며, aria-invalid만으로 외형을 검증했다고 간주하지 않는다.
- 공백만 있는 계정은 `TC-L-06`에서 다룬다.

### `TC-L-03` 계정이 null인 로그인 요청

- **요구사항 ID:** R-02
- **검증 목적:** 계정이 null인 직접 API 요청을 서버가 거부하는지 확인한다.
- **우선순위 / 이유:** P1 / 화면 검증을 거치지 않는 요청에서도 인증이 허용되지 않아야 하므로 핵심 인증 검증으로 분류한다.
- **테스트 레이어 / 선택 이유:** API / 화면의 입력 차단과 독립적으로 서버 인증 검증을 확인한다.
- **자동화 상태:** 구현
- **연결 코드:** [login.api.spec.js](../tests/login.api.spec.js)의 `[TC-L-03]` 테스트 (A·B 독립 실행)

#### 사전조건

- 서버가 실행 중이며 로그인 세션 쿠키가 없는 API 요청 컨텍스트를 준비한다.
- 각 조합은 독립적인 요청 컨텍스트에서 실행한다.

#### 입력값 및 장애 조건

| 조합 | JSON 요청 본문 |
|---|---|
| A | `{"username": null, "password": null}` |
| B | `{"username": null, "password": "demo1234"}` |

#### 수행 절차

1. `Content-Type: application/json`으로 해당 조합의 본문을 `POST /api/login`에 전송한다.
2. HTTP 상태 코드와 JSON 응답 본문을 확인한다.
3. 같은 요청 컨텍스트에서 `GET /api/me`를 호출해 인증 상태를 확인한다.
4. 각 조합에서 위 절차를 독립적으로 수행한다.

#### 기대 결과

- 두 조합 모두 로그인 응답은 HTTP 401이며, 본문의 `error`는 `계정 또는 비밀번호를 확인해 주세요.`이다.
- 이후 `GET /api/me`는 HTTP 401을 반환하여 비로그인 상태임을 확인한다.

#### 종료 후 정리

- API 요청 컨텍스트를 종료한다.

#### 비고

- 조합 A는 두 필드가 모두 null인 경우다. 조합 B는 올바른 비밀번호를 사용하여 계정 null 조건을 분리한다.
- null, 빈 문자열, 필드 생략은 서로 다른 입력이다. 빈 문자열과 필드 생략은 `TC-L-07`에서 다룬다.

- 첫 로그인 요청의 완료를 보류하고, 클라이언트의 10초 제한 처리는 정상 실행되도록 한다.
- 취소된 네트워크 요청은 응답을 전달할 수 없을 수 있다. 이 경우 앱 시작 전에 테스트용 fetch 대체 계층을 설치하여 첫 요청만 AbortSignal 이후에도 늦게 완료하도록 제어한다. 이는 응답 순서 검증을 위한 테스트 장치이며 제품의 취소 처리를 변경하지 않는다.
- 두 번째 요청은 실제 서버 응답과 세션 쿠키를 사용한다. 첫 요청의 늦은 성공 결과는 다른 사용자 이름(`bob`)을 넣어 잘못된 반영을 구별하고 세션 쿠키는 만들지 않는다.

#### 입력값 및 장애 조건

공통 입력: 계정 `alice`, 비밀번호 `demo1234`. 첫 요청은 t=10,000ms에 시간 초과된다.

| 조합 | 첫 요청의 늦은 결과 | 늦은 결과를 전달할 시점 |
|---|---|---|
| A | 200, `{"name":"bob","role":"user"}` | 시간 초과 후, 재시도 전 |
| B | 200, `{"name":"bob","role":"user"}` | 두 번째 요청 처리 중 |
| C | 401, 인증 실패 오류 본문 | 두 번째 요청 처리 중 |
| D | 200, `{"name":"bob","role":"user"}` | 두 번째 요청 성공 후 |
| E | 401, 인증 실패 오류 본문 | 두 번째 요청 성공 후 |

#### 수행 절차

1. 공통 입력값으로 첫 로그인을 제출하고 응답을 보류한다.
2. 10초를 진행하여 시간 초과 안내, 입력값 유지와 버튼 활성화를 확인한다.
3. A는 첫 요청의 늦은 결과를 전달하고 화면이 변하지 않는지 확인한 뒤 재제출한다. B~E는 먼저 [로그인]을 선택하여 두 번째 요청을 시작한다.
4. B·C는 두 번째 요청을 보류한 상태에서 첫 요청의 결과를 전달하고 처리 중 상태를 확인한다. 이후 두 번째 요청을 정상 완료한다.
5. D·E는 두 번째 요청의 정상 로그인 완료를 확인한 뒤 첫 요청의 늦은 결과를 전달한다.
6. 최종 사용자와 화면, 로그인 요청 수를 확인한다. 조합마다 독립 실행한다.

#### 기대 결과

- 시간 초과 시 확정된 지연 안내를 표시하고 입력값과 재제출 가능한 상태를 유지한다.
- A에서 늦은 성공 결과를 전달해도 로그인 화면과 시간 초과 안내가 유지되며 `bob`으로 로그인되지 않는다.
- B·C에서는 오래된 결과 때문에 두 번째 요청의 버튼 비활성 상태와 `로그인 중…`이 해제되지 않는다. 오래된 결과로 화면 전환이나 인증 오류 안내가 발생하지 않는다.
- 모든 조합에서 사용자 재제출로만 두 번째 요청이 발생하며 총 로그인 요청은 2건이다.
- 두 번째 요청의 200 응답 후 `alice · 멤버`, 로그아웃 버튼과 예약 화면이 표시된다. D·E의 오래된 결과도 이 상태를 변경하지 않는다.

#### 종료 후 정리

- 모든 보류 응답을 해제 또는 종료하고 가로채기·fetch 대체·시계 제어를 정리한다. 실제 생성된 세션으로 로그아웃 API를 호출한 뒤 컨텍스트를 닫는다. 실패 시에도 정리한다.

#### 비고

- 늦은 결과를 브라우저에 전달하지 못했다면 그 조합을 통과로 기록하지 않는다. 실제 완료 순서가 재현됐다는 증거를 남긴다.
- 이 케이스는 앱의 오래된 결과 무시를 검증한다. 실제 서버의 처리 취소·세션 미생성이나 브라우저 쿠키 경합까지 보장한다고 해석하지 않는다.
- 시간 초과 후 재시도의 제한 시간은 새 요청 시작 시점부터 계산한다. 두 번째 요청은 자신의 10초 한계 전에 완료시켜 첫 요청 결과의 영향을 분리한다.
- 로그인 요청은 테스트 전용 fetch 대체 계층(`controlled`)으로 보류·완료하여 요청 수와 완료 시점을 제어한다. 제품 코드의 요청·시간 초과 처리는 변경하지 않는다.

- **검증 목적:** 서버 로그아웃 완료 후 응답 유실 동작을 확인한다.
- **우선순위 / 이유:** P2 / 서버 처리 후 응답만 유실되는 드문 상황이며, 재시도나 보호 API의 401로 복구된다.
- **테스트 레이어 / 선택 이유:** E2E / 화면과 요청 결과의 연결을 확인한다.
- **자동화 상태:** 구현
- **연결 코드:** [login-resilience.e2e.spec.js](../tests/login-resilience.e2e.spec.js)의 `[TC-L-30]` 테스트 2개

#### 사전조건

- 조합별로 새 브라우저 컨텍스트와 전용 테스트 데이터를 사용한다. 초기 세션 확인을 완료한 뒤 대상 요청만 제어하며, 다른 API는 정상 통신한다.
- 실제 alice 세션으로 POST /api/logout을 서버까지 전달하여 세션 삭제를 완료한 뒤, 성공 응답 대신 브라우저에 네트워크 실패를 전달한다.

#### 입력값 및 장애 조건

| 조합 | 결과 불명 이후 사용자 동작 |
|---|---|
| A | 보호 API를 발생시키는 날짜 변경 |
| B | 로그아웃 재시도 |

#### 수행 절차

1. 실제 서버의 로그아웃 성공을 확인하되 브라우저에는 실패를 전달한다.
2. 결과 불명 안내와 현재 화면 유지를 확인한다.
3. A는 실제 보호 API의 401을 수신하고, B는 정상 로그아웃 재호출 응답을 받는다.

#### 기대 결과

- 처음에는 “로그아웃 완료를 확인하지 못했습니다. 다시 시도해 주세요.”를 표시한다.
- A는 401 수신 후 “로그인이 필요합니다. 다시 로그인해 주세요.”와 로그인 화면을 표시한다.
- B는 세션이 없어도 200과 {"ok":true}를 받아 로그인 화면으로 전환한다.

#### 종료 후 정리

- finally에서 장애·응답 보류·시계 제어를 해제한다. 생성한 예약은 소유자 세션으로 취소하고 관리자 잠금은 해제한다. 생성된 세션을 로그아웃하고 테스트 컨텍스트를 종료한다. 서버 재시작 케이스는 전용 서버를 종료하고 임시 DB를 제거한다.

#### 비고

- 서버 응답을 확보했다는 사실과 브라우저에는 전달되지 않았다는 사실을 모두 확인한다. 단순 요청 전 abort로는 이 상황을 재현할 수 없다.
