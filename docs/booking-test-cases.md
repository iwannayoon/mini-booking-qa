# 예약 테스트 케이스

상태: 자동화 반영 완료 · 작성일: 2026-11-08

## 1. 기준과 범위

- [최종 요구사항](requirements-final.md)의 R-10~23과 예약 데이터 저장·ID 발급 요구사항 N-01·N-04를 대상으로 한다.
- R-10의 미인증·관리자 권한·본인 조회·타인 취소는 [로그인 테스트 케이스](login-test-cases.md)의 `TC-L-31`~`TC-L-34`를 재사용한다. 아래 예약 흐름에서도 관련 결과를 확인한다.
- 모든 `TC-B` 케이스는 [예약 API 테스트](../tests/booking.api.spec.js)와 [예약 E2E 테스트](../tests/booking.e2e.spec.js)에 `[TC-B-xx]` 제목으로 자동화되어 있으며 자동화 상태는 [로그인 테스트 케이스](login-test-cases.md)와 같은 기준(미구현 / 부분 구현 / 구현)으로 표시한다. **구현**은 테스트 코드가 작성되었다는 의미이며 기능 구현 여부나 특정 실행의 통과를 의미하지 않는다.
- 케이스 ID는 `TC-B-01`부터 부여한다. 제목·ID와 실제 자동화 테스트 수는 일치하지 않을 수 있다.

## 2. 공통 사전조건과 정리

- 자동화는 전용 서버·실행별 임시 SQLite DB를 사용한다. 개인 개발 DB를 초기화하지 않는다.
- D는 테스트 시작 시 한 번 계산한 KST 내일이다. 시간 경계 케이스는 서버 시계를 별도로 고정하며, 브라우저 시간 변경만으로 서버 시간 검증을 대신하지 않는다.
- 예시 시간은 모두 KST 정각 시작 1시간 슬롯이며 API 값은 `YYYY-MM-DDTHH:00:00+09:00`이다.
- 별도 언급이 없으면 alice 인증 상태, 대상 슬롯은 미래·30일 미만·잠금 해제·확정 예약 없음이다. 각 조합에는 독립 데이터와 세션을 배정한다.
- 생성 ID·소유자·잠금 슬롯을 기록한다. finally에서 소유자 취소, 관리자 잠금 해제, 장애·시계 제어 해제와 로그아웃·컨텍스트 종료를 수행한다. 취소 이력은 남으므로 전체 목록 개수보다 대상 ID와 슬롯을 기준으로 판정한다.
- 여러 조합은 각각 결과를 기록한다. P1은 핵심 흐름·권한·무결성, P2는 경계·표시·복구 검증이다.
- 응답 대기는 조작 전에 등록하고 요청의 메서드·경로를 구분한다. 임의 sleep은 사용하지 않는다.
- 실행 일시·환경·결과·증거는 별도 [테스트 리포트](booking-test-report.md)에 기록한다. 이 문서는 테스트 설계이며 실행 결과를 담지 않는다.

### `TC-B-01` 예약 시작 시간과 영업시간 경계

- **요구사항 ID:** R-11, R-16
- **검증 목적:** 예약 시작 시간과 영업시간 경계 동작을 확인한다.
- **우선순위 / 이유:** P2 / 경계 조건·표시·복구 동작을 검증한다.
- **테스트 레이어 / 선택 이유:** API / 서버 규칙과 저장 결과를 화면과 독립적으로 확인한다.
- **자동화 상태:** 구현
- **연결 코드:** [booking.api.spec.js](../tests/booking.api.spec.js) › `[TC-B-01]` 테스트 4개

#### 사전조건

- 서버 시계를 KST 2030-01-10 10:00:00으로 고정한다. 브라우저 시계만 바꾸지 않는다. 시계 주입 또는 동등한 서버 제어가 필요하다.

#### 입력값 및 장애 조건

| 조합 | 입력·조건 |
|---|---|
| A | 2030-01-10 09:00 / 10:00 / 11:00 시작 |
| B | 2030-02-09 09:00 / 10:00 / 11:00 시작 |
| C | 2030-01-11 08:00 / 09:00 / 17:00 / 18:00 시작 |
| D | 2030-01-11 09:30 시작 |

#### 수행 절차

1. 각 시간을 +09:00 ISO slot으로 구성하여 예약 생성 API에 각각 요청한다.
2. 상태와 생성 여부를 확인하고 성공 예약을 정리한다.

#### 기대 결과

- A는 순서대로 400/400/201이다.
- B는 순서대로 201/400/400이다. 정확히 30×24시간 후는 거부한다.
- C는 400/201/201/400이며 D는 400이다.
- 거부된 요청은 예약을 생성하지 않는다.

#### 종료 후 정리

- 공통 정리 기준에 따라 생성한 예약·잠금·세션·장애 설정을 정리한다. 실패 시에도 finally에서 실행한다.

#### 비고

- 정각 조건을 만족하는 경계 인접 슬롯을 사용한다. 과거 날짜 때문에 영업시간 위반 검증이 가려지지 않도록 서버 시계를 고정한다.
- 시계 고정 전용 서버([clock-server.js](../tests/helpers/clock-server.js))에서 실행한다.

### `TC-B-02` 초기 날짜·슬롯 목록과 가용성 표시

- **요구사항 ID:** R-11, R-12

#### 종료 후 정리

#### 비고

- 시간 경계 자체는 TC-B-01에서 서버 기준으로 검증한다.
- 자동화는 서버 시계를 고정하지 않고 실제 시계를 서버·브라우저가 공유한다. 범위 밖 날짜는 어제와 +31일을 사용한다.

### `TC-B-24` 예약 저장 제약과 재연결 후 데이터 유지

- **요구사항 ID:** N-01, R-22
- **검증 목적:** 확정 예약 중복을 막는 부분 고유 인덱스와, DB 재연결 후 예약·잠금 데이터 유지를 확인한다.
- **우선순위 / 이유:** P1 / 저장 제약이 깨지면 같은 슬롯에 확정 예약이 중복되어 데이터 무결성이 깨진다.
- **테스트 레이어 / 선택 이유:** 통합 / API 동작과 분리하여 SQLite 저장 계층의 제약과 영속성을 직접 확인한다.
- **자동화 상태:** 구현
- **연결 코드:** [booking.api.spec.js](../tests/booking.api.spec.js)의 `[TC-B-24]` 테스트 2개

#### 사전조건

- A는 메모리 DB, B는 전용 임시 DB 파일을 사용한다. 공용 테스트 서버의 DB는 사용하지 않는다.

#### 입력값 및 장애 조건

| 조합 | 입력·조건 |
|---|---|
| A | 같은 슬롯에 confirmed 예약 2건 저장 시도, 이후 첫 예약 취소 후 재저장 |
| B | confirmed·cancelled 예약과 잠금 슬롯 저장 후 DB를 닫고 다시 연결 |

#### 수행 절차

1. A는 confirmed 예약을 저장한 뒤 같은 슬롯에 다른 confirmed 예약을 저장한다. 첫 예약을 cancelled로 바꾼 뒤 다시 저장한다.
2. B는 데이터를 저장하고 DB를 닫은 다음 같은 파일로 다시 연결하여 조회한다.

#### 기대 결과

- A의 두 번째 confirmed 저장은 거부된다. 첫 예약 취소 후에는 저장되며, 취소 행은 삭제되지 않아 전체 2건이 남는다.
- B는 재연결 후에도 예약 2건의 ID·상태와 잠금 슬롯이 그대로 조회된다.

#### 종료 후 정리

- DB 연결을 닫고 임시 DB 디렉터리를 삭제한다. 실패 시에도 finally에서 실행한다.

#### 비고

- B는 서버 프로세스 재시작 대신 저장 계층 재연결로 검증한다. 예약·잠금 조회는 모두 DB에서 읽으므로 서버 메모리 상태와 무관하다. 실제 프로세스 재시작은 `TC-L-26`에서 세션 기준으로 검증한다.

### `TC-B-25` 예약 ID 날짜별 순번 발급

- **요구사항 ID:** N-04, R-16
- **검증 목적:** 예약 ID가 KST 생성일과 날짜별 공통 순번으로 발급되고, 취소·재연결 후 유지되며 실패 시 롤백되는지 확인한다.
- **우선순위 / 이유:** P2 / ID 형식·순번 규칙 검증이다. 순번이 어긋나도 기본 키 제약으로 중복 저장은 거부된다.
- **테스트 레이어 / 선택 이유:** 통합·API / 자정 경계와 재연결은 저장 계층에서 시각을 지정해 확인하고, 슬롯별 발급과 실패 롤백은 실제 예약 API로 확인한다.
- **자동화 상태:** 구현
- **연결 코드:** [booking.api.spec.js](../tests/booking.api.spec.js)의 `[TC-B-25]` 테스트 2개

#### 사전조건

- A는 전용 임시 DB 파일을 사용하고 발급 시각을 직접 지정한다. B는 공용 테스트 서버에서 alice·bob 세션과 빈 슬롯 3개를 사용한다.

#### 입력값 및 장애 조건

| 조합 | 입력·조건 |
|---|---|
| A | KST 2026-09-28 23:59:59 발급 → 취소 → DB 재연결 → 롤백 → 재발급 → 2026-09-29 00:00:00 발급 |
| B | alice가 2개 슬롯 복수 예약, bob이 빈 슬롯과 점유 슬롯을 묶어 예약(409), bob이 빈 슬롯 단일 예약 |

#### 수행 절차

1. A는 각 단계에서 발급된 ID를 확인한다.
2. B는 각 예약 응답의 ID 형식과 순번을 비교한다.

#### 기대 결과

- A의 ID는 `20260928-0001`로 시작하며, 취소·재연결 후에도 순번이 이어지고(`-0002`), 롤백된 발급은 다시 같은 순번으로 발급된다. 자정 이후에는 `20260929-0001`부터 다시 시작한다.
- B의 ID는 오늘(KST) `YYYYMMDD-` 뒤에 최소 4자리 순번이 붙는 형식이다. 복수 예약은 슬롯마다 연속된 순번을 받는다.
- B에서 409로 실패한 요청은 순번을 소비하지 않아, 다음 예약이 직전 순번 +1을 받는다.

#### 종료 후 정리

- 생성한 예약을 소유자 세션으로 취소하고 임시 DB를 삭제한다. 실패 시에도 finally에서 실행한다.

#### 비고

- 요구사항의 "기존 UUID 유지"는 과거 데이터 이관 조건으로, 신규 발급만 다루는 이 케이스 범위 밖이다.
- B는 실제 생성 시각을 쓰므로 KST 자정 직전에 실행하면 날짜 접두어가 바뀔 수 있다.
